# 架构设计文档

> 本文档是 automation-platform 的概要设计与详细设计,覆盖整体架构、分层职责、
> 依赖关系、配置体系、测试分层与扩展点。供测试开发人员理解项目架构、技术选型
> 与设计决策。AI_RULES.md 的 16 条红线是本文档的约束前提。

## 1. 项目背景与目标

### 1.1 背景

企业内有多个业务系统(OMS/WMS/TMS/JMS 等),每个系统都需要接口自动化、WebUI
自动化、数据库校验等测试能力。传统做法是每个系统各写一套测试脚本,导致能力重复、
维护分散、标准不一。

### 1.2 目标

搭建一个企业级 Python 自动化测试平台:

- 共享框架内核(framework),各业务系统独立维护测试代码(projects)
- 覆盖接口自动化(API 优先)、Web 自动化(Playwright)、App 自动化(Appium)
- 支持数据库校验、Redis 缓存、Kafka/RabbitMQ/RocketMQ 消息队列
- 支持数据驱动、接口依赖编排、并发执行、Allure 报告
- 支持 GitLab CI / Jenkins / Docker
- 后续支持 AI Agent 扩展(失败分析、用例生成)

### 1.3 技术栈

| 类别 | 技术 | 版本约束 | 选型理由 |
| --- | --- | --- | --- |
| 语言 | Python | >=3.12 | asyncio 原生支持、类型系统成熟 |
| 测试框架 | pytest | >=8.3 | 生态最丰富、fixture 机制灵活 |
| 依赖管理 | uv | 最新 | 比 pip/poetry 快 10-100 倍、workspace 原生支持 |
| HTTP 客户端 | httpx | >=0.27 | 原生 async、HTTP/2、mock transport 支持好 |
| Web 自动化 | Playwright | >=1.40 | 跨浏览器、原生 async、自动等待、trace viewer |
| App 自动化 | Appium | >=2.0 | 跨平台、社区成熟 |
| 配置 | pydantic v2 + pydantic-settings | >=2.7 | 类型安全、多源合并、env 覆盖 |
| 日志 | loguru | >=0.7 | 零配置、结构化、文件轮转 |
| 数据库 | SQLAlchemy | >=2.0 | async engine、多方言、连接池 |
| 缓存 | redis | >=5.0 | async 支持、连接池 |
| 消息队列 | aiokafka / aio-pika / rocketmq | 最新 | 三端 async 客户端 |
| 报告 | allure-pytest | >=2.13 | 行业标准、富文本报告、历史趋势 |
| 并发 | pytest-xdist | >=3.5 | 进程级并行、隔离性好 |
| 代码质量 | ruff + mypy | 最新 | ruff 替代 flake8+isort+black,mypy strict |
| CI/CD | GitLab CI + Jenkins | -- | 双流水线共用 scripts/ci/ci.sh |

### 2.2 核心设计原则

| 原则 | 说明 | 来源 |
| --- | --- | --- |
| 单向依赖 | framework 不依赖 projects,下层不依赖上层 | AI_RULES 第 11 条 |
| 模块化 | 新功能必须模块化,禁止业务代码进入 framework | AI_RULES 第 2/3 条 |
| 公共能力抽象 | 所有公共能力必须抽象到 framework | AI_RULES 第 4 条 |
| 不复制代码 | 重复逻辑抽象为公共方法,禁止复制 | AI_RULES 第 8 条 |
| 资源显式释放 | 连接/客户端/浏览器用完即关,优先 async context manager | AI_RULES 第 12 条 |
| 测试隔离 | 单元测试 mock/fake,不连真实网络/DB/Redis/MQ | AI_RULES 第 14 条 |
| 异步无阻塞 | 异步上下文禁止 time.sleep/requests 等同步阻塞 | AI_RULES 第 16 条 |
| 配置外置 | 密钥/环境配置走 YAML + env,禁止硬编码 | AI_RULES 第 10 条 |

## 3. framework 模块详细设计

### 3.1 core/ -- 核心层

| 模块 | 职责 | 关键导出 |
| --- | --- | --- |
| `config.py` | 多环境配置中心:YAML + env + .env 三源合并 | `FrameworkSettings`, `get_settings()`, `AppEnv` |
| `logger.py` | loguru 结构化日志:控制台+文件+异常+请求日志 | `get_logger()`, `setup_logging()`, `log_request()` |
| `context.py` | 测试上下文 + trace_id 关联(contextvars) | `TestContext`, `current_trace_id()`, `trace()` |
| `exceptions.py` | 统一异常层级(FrameworkError 基类) | `FrameworkError`, `ClientError`, `ConfigError` 等 |
| `recorder.py` | HTTP 请求/响应记录器(失败留痕用) | `RequestRecorder`, `record_exchange()` |

**配置体系(核心)**:

```
优先级高 -> 低:
  1. 代码传参 FrameworkSettings(...)
  2. 环境变量 APP_* (嵌套用 __ 分隔,如 APP_WEB__HEADLESS)
  3. .env 文件
  4. config/envs/<APP_ENV>.yaml
  5. 模型字段默认值
```

配置模型层级:`FrameworkSettings` -> `HttpSettings` / `WebSettings` / `DatabaseSettings` /
`RedisSettings` / `MQSettings` / `AppSettings` / `AISettings` / `NotificationSettings`。
每个嵌套模型可通过 `APP_<节>__<字段>` 环境变量覆盖。

### 3.2 clients/ -- 能力客户端层

所有客户端遵循统一模式:lazy 初始化 + async context manager + 异常包装为 ClientError。

| 客户端 | 模块 | 核心类 | 依赖 | 说明 |
| --- | --- | --- | --- | --- |
| HTTP | `clients/http/` | `AsyncHttpClient` | httpx | 重试/鉴权/日志/redaction/mock transport |
| Web | `clients/web/` | `WebClient` | playwright | 导航/交互/截图/channel 支持 |
| App | `clients/app/` | `AppClient` | appium | Appium Driver 封装 |
| DB | `clients/db/` | `DatabaseClient` | sqlalchemy | MySQL/PG/Oracle/ClickHouse,async engine |
| Cache | `clients/cache/` | `RedisClient` | redis | async 连接池 |
| MQ | `clients/mq/` | `MessageClient` | aiokafka/aio-pika/rocketmq | 统一接口,Kafka/RabbitMQ/RocketMQ 三端 |

**关键设计**:所有可选依赖(playwright/appium/redis/rocketmq/aio-pika)均为 lazy import,
未安装时不影响框架运行,首次使用时才报明确错误。

### 3.3 testing/ -- 测试基础设施层

| 模块 | 职责 | 关键导出 |
| --- | --- | --- |
| `datadriven/` | YAML 数据驱动加载 | `load_cases()`, `case_ids()` |
| `dependency/` | 接口依赖 DAG 编排 | `DAG`, `VariableManager` |
| `extractors/` | JSONPath/JMesPath 响应提取 | `extract()` |
| `assertions/` | 断言库:response/json/schema/database | `assert_response()`, `SoftAssert` |
| `hooks/` | pytest 插件:env 初始化/trace 上下文/失败截图 | `fixtures`, `ScreenshotProvider` |
| `data/` | 数据生命周期管理(创建/清理) | `DataLifecycle` |

**数据驱动模式**:

```python
_CASES = load_cases(Path("data/login_cases.yaml"))

@pytest.mark.parametrize("case", _CASES, ids=case_ids(_CASES))
async def test_login(case: dict[str, Any]) -> None:
    ...
```

### 3.4 reporting/ -- 报告层

| 模块 | 职责 |
| --- | --- |
| `allure.py` | Allure step/attach 装饰器(allure 未装时 no-op) |
| `labels.py` | 动态标签:severity/feature/story/issue/link |
| `environment.py` | 写 environment.properties + categories.json |
| `history.py` | Allure 历史趋势:保留上次结果 + 复制到新结果 |
| `notification.py` | 邮件通知:发送 Allure 报告链接 |

### 3.5 plugins/ai/ -- AI 扩展层

| 模块 | 职责 |
| --- | --- |
| `base.py` | `FailureAnalyzer` ABC:失败分析接口 |
| `null_analyzer.py` | 空实现(未配置 AI 时使用) |
| `llm_analyzer.py` | LLM 实现(OpenAI 兼容接口) |
| `generator.py` | AI 用例生成(预留) |

## 4. projects/ -- 业务测试工程层

### 4.1 目录约定

每个业务项目统一结构(复制 `projects/template`):

```
projects/<system>/
├── api/            # 接口封装(API 项目)
├── pages/          # Page Object(WebUI 项目)
├── testcase/       # 测试用例
├── data/           # 测试数据(yaml 数据驱动)
├── fixture/        # 项目级 fixtures
├── config/envs/    # 环境配置(dev/test/uat/prod .yaml)
├── sql/            # SQL 脚本(可选)
├── conftest.py     # 项目级 conftest(框架插件 + 配置定位)
├── pyproject.toml  # 项目元数据 + uv workspace source
├── pytest.ini      # pytest 配置
└── README.md       # 项目说明
```

### 4.2 命名约定

JMS 系统按国家部署:`jms` + 2 位地区代码。

| 文件夹 | 地区 | 类型 |
| --- | --- | --- |
| `jmseg` | 埃及(EG) | API 自动化 |
| `jmseu` | 德国(EU) | WebUI 自动化 |

其他系统直接用缩写:`oms` / `wms` / `tms`。

### 4.3 conftest.py 职责

每个项目的 `conftest.py` 做三件事:

1. `os.environ.setdefault("APP_CONFIG_DIR", ...)` -- 指向本项目 `config/envs`
2. `pytest_plugins = ["framework.testing.hooks.fixtures"]` -- 启用框架 pytest 插件
3. re-export 项目级 fixtures -- 让测试用例按名请求

### 4.4 测试隔离设计

- **API 项目**:默认用 `httpx.MockTransport` 模拟后端,不连真实网络(AI_RULES 第 14 条)
- **WebUI 项目**:默认注入 `_FakePage` 模拟 Playwright 页面,无需浏览器
- **真实环境**:设环境变量切换(如 `JMSEU_REAL_BROWSER=1`),走真实服务/浏览器

## 5. CI/CD 架构

### 5.1 流水线

```
代码提交 -> 安装依赖(uv sync --frozen) -> lint(ruff) -> smoke(@smoke) -> regression(@regression) -> Allure 报告 -> 发布
```

### 5.2 统一入口

`scripts/ci/ci.sh` 是 GitLab CI 和 Jenkins 共用的唯一入口,避免命令重复:

```bash
sh scripts/ci/ci.sh install      # uv sync --frozen + allure-pytest
sh scripts/ci/ci.sh smoke        # pytest -m smoke
sh scripts/ci/ci.sh regression   # pytest -m regression
sh scripts/ci/ci.sh report       # 生成 Allure HTML
```

### 5.3 测试分级

| marker | 用途 | 时机 |
| --- | --- | --- |
| `@pytest.mark.smoke` | 关键路径,快速门禁 | 每次提交 |
| `@pytest.mark.regression` | 全量回归 | 回归阶段 |

`pytest.ini` 已注册 marker 并启用 `--strict-markers`(未注册 marker 报错)。

## 6. uv Workspace 架构

### 6.1 工作区结构

```
automation-platform/           # 根 pyproject.toml
├── pyproject.toml             # [tool.uv.workspace] members = ["framework", "projects/jmseu", ...]
├── .venv/                     # 唯一 venv(所有 workspace 成员共享)
├── framework/                 # workspace 成员(hatchling + src 布局)
│   └── [tool.uv.sources]      # 无需(自身就是 framework)
└── projects/
    └── jmseu/
        └── [tool.uv.sources]  # framework = { workspace = true }
```

### 6.2 关键配置

根 `pyproject.toml`:

```toml
[tool.uv.workspace]
members = ["framework", "projects/jmseu"]  # 新增项目时加入

[tool.uv.sources]
framework = { workspace = true }  # framework 解析为本地 workspace 包
```

项目级 `pyproject.toml`:

```toml
[project]
dependencies = ["framework", ...]

[tool.uv.sources]
framework = { workspace = true }  # 声明 framework 为 workspace 依赖
```

### 6.3 IDE 配置

PyCharm 解释器必须指向**平台根**的 workspace venv:

```
C:\work\PythonProject\automation-platform\.venv\Scripts\python.exe
```

不要选 `projects/<system>/.venv`(空壳)或 `pytest.exe`(应选 `python.exe`)。

## 7. 关键设计决策

| 决策项 | 方案 | 原因 |
| --- | --- | --- |
| 依赖管理 | uv | 速度快、workspace 原生支持、lock 可复现 |
| 异步模型 | asyncio + async/await | IO 密集型测试场景、避免阻塞 |
| 配置中心 | pydantic-settings + YAML + env | 类型安全、多源合并、env 覆盖灵活 |
| 可选依赖 | lazy import | playwright/appium 等未装不影响框架运行 |
| 测试隔离 | MockTransport / FakePage | 单元测试不连真实网络/浏览器(AI_RULES 第 14 条) |
| MQ 抽象 | MessageClient 统一接口 | Kafka/RabbitMQ/RocketMQ 可互换 |
| AI 扩展 | FailureAnalyzer ABC + NullAnalyzer | 未配置 AI 时 no-op,配置后即用 |
| CI 入口 | scripts/ci/ci.sh 统一脚本 | GitLab/Jenkins 共用,避免命令重复 |
| 报告 | allure-pytest(可选) | 未装时 step/attach no-op,装上即用 |

## 8. 扩展指南

### 8.1 新增能力客户端

1. 在 `framework/clients/<name>/` 创建模块
2. 遵循统一模式:lazy import + async context manager + 异常包装
3. 配置项加到 `core/config.py` 的 `FrameworkSettings`(嵌套模型)
4. 在 `clients/__init__.py` 导出
5. 写单元测试(`tests/unit/clients/test_<name>.py`,mock 外部依赖)
6. 更新 `__all__` 和本文档

### 8.2 新增业务系统

1. 复制 `projects/template` 为 `projects/<name>`
2. 改 `pyproject.toml` 的 `name`
3. 加入根 `pyproject.toml` 的 `[tool.uv.workspace] members`
4. 配置 `config/envs/*.yaml`
5. 写 `conftest.py`(定位 config + 启用框架插件 + re-export fixtures)
6. 编写 `api/` 或 `pages/` + `testcase/`

### 8.3 新增国家(JMS 系列)

1. 复制 `projects/template` 或已有 JMS 项目为 `projects/jms<code>`
2. 同 8.2 步骤 2-6
3. 创建 `docs/业务留痕-<国家>.docx`(结构复制已有业务留痕)

## 11. 接口压测引擎

### 11.1 概述

`projects/loadtest/` 是独立的接口压测项目, 基于 Locust + framework `testing.load` 模块.
使用 YAML 驱动压测场景, 支持按国家隔离, 多格式数据源, 业务级 JSON 断言,
阶梯式加压找瓶颈, 自动生成 HTML 报告.

### 11.2 核心组件

| 组件 | 实现位置 | 说明 |
| --- | --- | --- |
| 数据准备 (Data Provider) | `framework/testing/load/data_provider.py` | 模板引擎: `{{data.file.col}}`, `{{uuid}}`, `{{random.int}}` |
| API 封装 | `projects/loadtest/runner.py` | YAML 场景 -> Locust HttpUser @task |
| 压测引擎 | `framework/testing/load/shapes.py` + Locust | YAML 驱动 ramp-up/hold/ramp-down |
| 监控 | `framework/testing/load/metrics.py` | p50/p90/p99 延迟, 错误率, RPS, 时间序列 |
| 结果展示 | `framework/testing/load/report.py` | HTML 报告 (SVG 图表, APDEX, SLA 断言) |
| SLA 断言 | `framework/testing/load/assertions.py` | 压测结束后评估全局指标 |
| 业务断言 | `runner.py` `assert_json` | 响应 JSON 体业务字段校验 (如 `succ: true`) |

### 11.3 数据源拉取脚本

`projects/loadtest/scripts/fetch_data.py` 从生产运单库分页查询数据, 写入 CSV/TXT:

- 数据源接口: `waybillouterapi/order/waybillTimeRangePage` (分页查询, MyBatis-Plus IPage)
- 并发拉取: 每批 40 页并发, 整批全空即停
- `--count N`: 按条数拉取, 自动计算页数
- `--start-time` / `--end-time`: 可配置查询时间范围
- 文件不覆盖: 同名文件自动加序号后缀
- CSV 只含动态字段 (11 列), 固定值 (productTypeId/customerId/smMode) 在 JMeter 写死
- CSV 兼容 Locust `{{data.*}}` 和 JMeter `${列名}` 两种引用方式

### 11.4 压测形状

| 形状文件 | 场景 | 说明 |
| --- | --- | --- |
| `load_profile_jmsbr.yaml` | 完整压测 | 200 并发, ramp-up 2min -> hold 56min -> ramp-down 2min (1 小时) |
| `load_profile_jmsbr_stepped.yaml` | 阶梯加压 | 50->100->150->200->300->400->500 用户, 每档 2min (14 分钟) |

### 11.5 运行方式

```powershell
# 一个 PyCharm 配置, 参数切换场景
python run.py waybill_get -t 10s                # 快速调试, 1 个用户
python run.py waybill_get -t 10s -u 200 -r 20   # 200 并发, 10 秒
python run.py waybill_get --shape -t 3600s        # 完整压测形状 (1 小时)
python run.py waybill_get --shape -p load_profile_jmsbr_stepped -t 840s  # 阶梯加压
```

JMeter 参数对照: 线程数 -> `-u`, Ramp-Up 时间 -> `-r` (换算: spawn-rate = 线程数 / Ramp-Up 时间)

### 11.6 QPS 计算

```
QPS = 并发用户数 / 平均响应时间(秒)
```

示例: 200 并发用户, 平均响应时间 332ms -> QPS = 200 / 0.332 = 602 QPS

## 12. 测试管理平台

测试管理平台由 `server/` 与 `frontend/` 组成, 采用 FastAPI + Vue 3 + Element Plus.
它不改变现有 pytest 用例结构, 通过项目扫描、subprocess 执行、allure-results 解析实现查用例、跑用例、看报告的闭环.

| 能力 | 说明 |
| --- | --- |
| 项目扫描 | 自动识别 `projects/` 下可执行项目、环境与测试文件 |
| 用例查询 | 解析函数、docstring、pytest marker、数据驱动 YAML |
| 测试执行 | `APP_ENV` 隔离环境, subprocess 调 pytest, WebSocket 推日志 |
| 报告查看 | 解析 allure-results, 展示通过率、结果分布、用例明细 |

详细设计和运行方式见 `docs/测试管理平台技术方案.md`。
